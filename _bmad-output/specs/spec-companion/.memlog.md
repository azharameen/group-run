- (capability) CAP-1: User can converse with AI agents via chat interface that routes intent to specialist teams
- (capability) CAP-2: Agents can invoke tools (filesystem read/write, MCP adapters, memory operations) during conversation
- (capability) CAP-3: Agents maintain long-term memory across conversations using memory middleware
- (capability) CAP-4: Agents load and execute skill files from configured skills directory
- (capability) CAP-5: Destructive filesystem operations (write, delete, overwrite) require human approval before execution
- (capability) CAP-6: User can create, list, view, update, delete, and archive ideas with agentic research attached
- (capability) CAP-7: Agents perform autonomous research on ideas including prior art search and analysis
- (capability) CAP-8: Platform loads MCP servers from config (stdio + HTTP) and user can add HTTP-only MCP servers via UI
- (capability) CAP-9: Agents read and write workspace files through CompositeBackend with route-based permissions
- (capability) CAP-10: Teams and agents are defined in YAML configuration files, loaded at startup, reloadable without restart
- (capability) CAP-11: Agent activity streams to frontend in real-time via SSE with structured event types
- (capability) CAP-12: Conversations are organized into persistent threads with full message history
- (capability) CAP-13: User can browse and search knowledge base documents that feed agent research
- (capability) CAP-14: Ideas page displays all ideas with filtering, scoring, and detail views
- (capability) CAP-15: System provides health checks, statistics, and observability endpoints
- (constraint) LangGraph 0.6.x + DeepAgents 0.6.8 are the sole orchestration paradigm — transitions lib, FSM states, YAML persistence, and custom SSE bus are dead code
- (constraint) 2-service split only: Frontend (React/Vite SPA + Nginx) and Backend (FastAPI + LangGraph in-process) — no 3rd microservice
- (constraint) SQLite via SqliteSaver is the sole database — single global singleton connection, no new connections
- (constraint) graph.astream(input, version='v2') is the only streaming API — stream_events(version='v3') is LangGraph 1.2+ only
- (constraint) No sandbox or code execution — agents cannot execute arbitrary code
- (constraint) Workspace filesystem is source of truth for ideas and artifacts — DB stores runtime state only
- (constraint) LANGGRAPH_STRICT_MSGPACK=true mandatory in all environments — startup fails fast if missing
- (constraint) All agent filesystem access goes through CompositeBackend with explicit route mappings
- (constraint) MCP tools bypass CompositeBackend permissions model — known security gap
- (constraint) config/mcp.json for platform-level MCP (stdio + HTTP); users can add HTTP-only MCP servers via UI stored in DB
- (constraint) Teams and agents defined in config/teams.yaml — loaded at startup, reloadable without restart
- (constraint) Config loading precedence: teams.yaml → mcp.json → DB overlay → env vars (highest)
- (constraint) All background work runs in-process — no Celery/RQ, no separate workers
- (constraint) Docker-based deployment with docker-compose — APP_ROOT_DIR pins workspace root
- (constraint) Frontend uses custom SSE hooks (useChatStream) — no langchain-react or AI SDK
- (constraint) Python 3.12, FastAPI 0.115.x, React 18.3.x, Vite 5.4.x, TypeScript 5.5.x, Tailwind 3.4.x
- (constraint) UUIDs v4 for all entities, ISO 8601 with timezone for dates, snake_case backend / camelCase frontend
- (constraint) Route files < 150 lines, services/repositories < 200 lines, agent runtime < 200 lines
- (constraint) API response time < 500ms, SSE event latency < 200ms, state transition < 2s
- (constraint) Never fabricate output — no silent fallback to fabricated agent success
- (decision) Supervisor agent routes user intent to domain-specialist teams via tool calling; teams are LangGraph subgraphs
- (decision) HITL uses LangGraph Command-based interrupts — approval requests persisted in SQLite
- (decision) Dependencies flow downward only: API → Orchestrator → Agent Runtime → Tools/Backends → Storage
- (decision) Comprehensive testing: pytest + pytest-asyncio for backend, Vitest/React Testing Library for frontend, E2E testing
- (decision) Old Siemens-specific code (scoring pipeline, research pipeline, FSM, transitions) is dead code and must be deleted
- (assumption) Solo developer context — architecture optimized for maintainability over operational simplicity
- (assumption) Postgres migration deferred until measurable bottlenecks (connection contention, WAL lock waits > 100ms p99)
- (assumption) JWT authentication deferred — session-based auth sufficient for current scope
- (assumption) Major version upgrades reviewed quarterly, applied every 6 months at minimum
- (question) Connector framework scope: Slack, Gmail, Drive, Calendar, Azure DevOps, Firebase, GitHub, Perplexity — which connectors are priority for initial release?
- (question) Frontend testing framework: Vitest or Jest? Current project uses Vite so Vitest is the natural fit but needs confirmation
- (question) E2E testing framework: Playwright or Cypress? Playwright is recommended for modern stacks but needs confirmation
