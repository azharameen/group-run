## What Went Well

### 1. Backend-First Architecture Discipline
Stories 5.1-5.4 built solid backend foundations before frontend stories (5.6-5.7) consumed them via clean API contracts. No API contract changes between backend and frontend implementation.

### 2. Review Patches Caught Real Bugs
Story 5.6 had 7 review patches applied: `animate-textured` typo, form clearing race conditions, NaN guards for numeric inputs, delete dialog handling, API error handling gaps, distinct Network icon usage, and connection status polling logic.

### 3. Modular Component Design
The `MCPManager.tsx` component followed a clear pattern: API client → component → settings integration. This pattern was reused for `TeamConfig.tsx`, improving frontend development velocity.

### 4. Config-Driven Architecture Validated
Dynamic LangGraph construction based on config files proved to be a solid architectural choice. The config precedence chain (`teams.yaml` → `mcp.json` → DB overlay → env vars) was maintained correctly across all stories.

## Challenges and Growth Areas

### 1. Story Spec Persistence Gap (HIGH)
**Dana (QA Engineer):** "Only 3 of 8 story specs were persisted. Stories 5.1-5.3 were implemented early in the session without spec files, and 5.7-5.8 specs weren't saved."

**Impact:** Lost detailed intent contracts, I/O matrices, task breakdowns, and review logs for 5 of 8 stories.

**Lesson:** Story spec creation must be mandatory before implementation starts.

### 2. Subagent Implementation Failures
Story 5.6 had the subagent fail to implement the MCPManager component. Manual fallback was needed, which took longer than expected.

**Root Cause:** Subagent instructions were too high-level; component requirements needed explicit task breakdowns with file-level details.

**Lesson:** Skill-based subagents need concrete task specs with explicit file paths, imports, and data flow diagrams.

### 3. Config Reload Race Conditions
Story 5.2's config reload mechanism had race condition concerns — initial design didn't account for concurrent reload requests. File lock mechanism implemented as mitigation.

**Lesson:** Config management APIs need concurrent access protection from the start.

### 4. Windows Unicode Encoding Issues
Multiple Python scripts failed with `UnicodeEncodeError` on Windows — emoji characters in config files can't encode to cp1252.

**Lesson:** Python scripts in cross-platform projects need `PYTHONIOENCODING=utf-8` or explicit encoding handling.

### 5. Complex Dynamic Graph Construction
Story 5.4 (TeamSubgraphFactory) was the most architecturally complex story. Building dynamic LangGraph structures at runtime from YAML is fundamentally different from static graph building.

**Lesson:** Dynamic graph construction needs dedicated testing per team configuration, not just unit tests.

## Key Insights and Learnings

### 1. Configuration-Driven Systems Require Validation Layers
Every config-driven feature (MCP servers, team structures) needs:
- Schema validation before loading
- Graceful fallback on invalid configs
- Clear error messages for user corrections

### 2. Adversarial Code Review is Worth the Investment
Story 5.6 review caught 7 bugs that would have reached production. The multi-layer review (Blind Hunter + Edge Case Hunter) found different categories of issues:
- **Blind Hunter:** Logic bugs, error handling gaps
- **Edge Case Hunter:** Numeric edge cases, concurrency issues, UI state bugs

### 3. API Client Separation Improves Maintainability
Putting API calls in dedicated `api/` files (`api/mcp.ts`, `api/team.ts`) keeps components clean and testable.

### 4. Dynamic Systems Need Dynamic Testing
Static unit tests aren't enough for config-driven systems. Need:
- Integration tests with various config combinations
- Config validation tests
- Error recovery tests

### 5. Retro Action Follow-Through was 0% (CRITICAL)
We committed to 3 action items in Epic 4 retro and completed 0. This is a system failure, not an individual failure.

### 6. Story Spec Persistence is Critical
Lost specs mean lost acceptance criteria, I/O matrices, and technical decisions. This makes future maintenance harder.
